# 実装方針・調査結果（設計ドキュメント）

このドキュメントは、「楽天ROOM運用の自動化」をどこまで・どうやって進めるかをまとめたものです。
専門用語はできるだけ避けていますが、わからない言葉が出てきたら遠慮なく質問してください。

## 1. 結論（まずここだけ読めばOK）

- 商品を探す・条件で絞り込む・重複をチェックする・紹介文を作る・候補一覧を保存する
  → **公式のデータだけを使い、自分のパソコン（このプロジェクト）の中だけで完結する処理なので、自動化して問題ありません。**
- 楽天ROOMへ実際に投稿するボタンを押す部分
  → **自動化しません。** 楽天ROOMの利用規約で「機械的に投稿する行為」がはっきり禁止されているためです。
  最終的に「コピペして投稿する」のは人間（あなた）が行います。

つまりこのプロジェクトは「投稿の下ごしらえを全自動化し、投稿ボタンを押す瞬間だけ人間が行う」という設計にします。

## 2. 調べたこと

### 2-1. 楽天ROOMの利用規約について

楽天ROOMの利用規約（禁止事項）には、次のような趣旨の記載があります。

> スクリプトその他のプログラムを実行する等の方法により、機械的に投稿、コメント等をする行為を禁止する

参考：
- [利用規約 - ROOM - 楽天市場](https://room.rakuten.co.jp/signup/agreement)
- [投稿のガイドライン - ROOM - 楽天市場](https://room.rakuten.co.jp/info/help/guideline/01.html)

つまり「ROOMへの投稿を、プログラムが自動でボタンを押して行う」ことは規約違反にあたる可能性が高く、
アカウント停止（BAN）のリスクがあります。世の中には「自動投稿ツール」を作って公開している人もいますが、
規約違反のリスクを利用者が負う形になっているため、このプロジェクトでは採用しません。

### 2-2. 楽天が公式に提供しているAPI（データ取得の仕組み）

楽天には「楽天ウェブサービス（Rakuten Web Service, 通称RWS）」という、開発者向けに公式に提供されている
データ取得の仕組み（API）があります。この中の「楽天市場 商品検索API（Ichiba Item Search API）」を使うと、
以下のような情報を**合法的に**取得できます。

- 商品名、価格、商品ページのURL、商品画像のURL
- レビュー平均点（reviewAverage）
- レビュー件数（reviewCount）
- ショップ名、ジャンル（カテゴリ）情報
- 商品の説明文（キャッチコピー）

参考：
- [Rakuten Web Service: Rakuten Ichiba Item Search API](https://webservice.rakuten.co.jp/documentation/ichiba-item-search)

利用するには「楽天会員登録」と「楽天ウェブサービスの利用登録（無料）」を行い、
「アプリID（applicationId）」と呼ばれる鍵となる文字列を発行してもらう必要があります。
2026年のAPI基盤刷新以降は、これに加えて「アクセスキー（accessKey）」も必要になりました。
これらは合言葉のようなもので、他人に見せたり、GitHubなどにそのまま公開したりしてはいけません
（このプロジェクトではGitHubのRepository Secretsに保存し、コードやログには一切出力しません）。

このAPIには「1秒間に送れるリクエストの数」などの利用制限（レート制限）があります。
短時間に大量アクセスすると制限にかかったり、利用停止になる可能性があるため、
プログラム側で「少し間隔を空けて呼び出す」処理を必ず入れます。

> 補足：APIのレスポンスに「楽天ROOM対象商品かどうか」を直接示す項目は現時点では見当たりませんでした。
> 実務上は「楽天市場で購入できる商品はROOMにも投稿できる」という前提で問題ありませんが、
> 実際に運用しながら例外がないか確認していきます。

### 2-3. ログイン・認証の扱いについて

このプロジェクトで「ログイン」が必要になるのは、商品データを取るための
「楽天ウェブサービスのアプリID」だけです。これはIDとパスワードでログインするタイプの認証ではなく、
発行された文字列（鍵）をプログラムに渡すだけの仕組みです。

- 楽天ROOM自体へのログイン（メールアドレスやパスワード）は、このプロジェクトでは**一切扱いません**。
  自動投稿をしない設計にしているため、ROOMにログインする必要自体がないからです。
- アプリID（鍵）は `.env` という設定ファイルに書き、`.gitignore` でGitの管理対象から除外します。
  これにより、間違ってGitHubに公開してしまう事故を防ぎます。

### 2-4. BANリスクを避けるための方針まとめ

| やること | 安全性 |
|---|---|
| 公式API（楽天ウェブサービス）でデータ取得 | ◎ 安全（利用規約で認められた使い方） |
| 取得したデータをローカルで条件判定・重複チェック | ◎ 安全（自分のPC内の処理） |
| 紹介文をテンプレートで自動生成 | ◎ 安全（自分のPC内の処理） |
| 候補一覧をファイルに保存し、人間が見て選ぶ | ◎ 安全 |
| ROOMのサイトを自動操作してログイン・投稿する | × 行わない（規約違反・BANリスク） |
| ROOMのページをスクレイピング（プログラムで読み取り）する | × 行わない（規約違反・負荷をかけるリスク） |

## 3. 自動化する処理の全体像

```
[1] 商品候補の収集
     楽天ウェブサービスAPIに「掃除」「収納」「キッチン 便利グッズ」などのキーワードで検索をかけ、
     商品情報（価格・レビュー評価・レビュー件数など）を取得する。

        ↓

[2] 条件判定（フィルタリング）
     以下の条件を満たす商品だけを残す。
       ・レビュー評価が4.0以上
       ・レビュー件数が100件以上
     （広告対象かどうか、ポイント倍率、ランキング入賞、メディア掲載の有無は判定材料にしない）

        ↓

[3] 重複チェック
     「過去に紹介した商品の一覧（data/posted_items.json）」と商品IDを突き合わせ、
     すでに紹介した商品を候補から除外する。

        ↓

[4] 紹介文の自動生成
     商品名・特徴・価格などから、
       ・自然な日本語の紹介文
       ・箇条書き（特徴のポイント）
       ・ハッシュタグ
     を1つの文章ブロックにまとめる（500文字以内、コピペしてそのまま使える形）。

        ↓

[5] 投稿候補一覧の保存
     [1]〜[4]の結果を1つのファイル（CSVまたはJSON）にまとめて保存する。
     ここまでは完全自動。

        ↓

[6] 人間による確認・投稿
     保存された候補一覧を人間が見て、内容と商品画像が合っているか確認したうえで、
     良いと思った紹介文をコピーし、楽天ROOMアプリ／サイトに手動で貼り付けて投稿する。
     投稿し終えたら、その商品IDを data/posted_items.json に追加する
     （これも将来的には「投稿しました」ボタンひとつで自動記録できるようにする想定）。
```

## 4. 開発の進め方（フェーズ分け）

最初から全部を作ろうとすると難しいので、小さく段階を踏みます。

- **フェーズ0（完了）**：設計・調査・最小構成のひな形作成
- **フェーズ1（完了）**：楽天ウェブサービスAPIから実際に商品を取得し、条件判定・重複チェック・
  紹介文生成・候補一覧の保存までを自動で行い、GitHub Actionsから手動実行できるようにした
- **フェーズ2（今後）**：使い勝手の改善（キーワードの追加、除外ワード、生成される文章の質の調整など）
- **フェーズ3（任意）**：投稿済み管理を楽にするための、人間向けの簡単なチェック用画面や記録の仕組み
  （※ここでも「ROOMへの自動投稿」は行いません）

### フェーズ1の実装に関する補足（2026年の楽天API仕様変更について）

楽天ウェブサービスは2026年にAPIの基盤を刷新しました。主な変更点は次のとおりです。

- APIのURL（ドメイン）が `app.rakuten.co.jp` から `openapi.rakuten.co.jp` に変わった
- 認証に「アプリID」だけでなく「アクセスキー」も必要になった
- 古いAPIは順次使えなくなる（すでに使えなくなっている可能性が高い）

このプロジェクトは調査時点で確認できた最新の情報をもとに実装していますが、この作業を行った
ネットワーク環境の制約により、楽天の公式ドキュメントページに直接アクセスして最終確認することは
できませんでした。そのため、実際にGitHub Actionsを実行してみてエラーになる場合は、以下を確認してください。

1. [楽天ウェブサービスの商品検索APIドキュメント](https://webservice.rakuten.co.jp/documentation/ichiba-item-search)
   で最新のエンドポイントURLを確認する
2. `config/settings.yaml`（無ければ`config/settings.example.yaml`をコピーして作成）の
   `api_endpoint` の値を最新のURLに書き換える
3. GitHubのRepository Secretsに登録した `RAKUTEN_APP_ID` ・ `RAKUTEN_ACCESS_KEY` の値が
   楽天ウェブサービスの管理画面に表示されているものと一致しているか確認する

コード自体を変更しなくても設定ファイルの書き換えだけで対応できるようにしてあります。

### HTTP 403エラーが出た件について（追加調査・対応）

実際にGitHub Actionsを実行したところ、認証情報は正しく渡っているにもかかわらずHTTP 403
（アクセス拒否）が返ってくることが分かりました。追加で調べたところ、2026年の刷新後の楽天ウェブサービスは
「ブラウザからのアクセス」を前提にした仕組みになっており、次の対応をしないと403で拒否されることが分かりました。

- リクエストに **Origin** ヘッダーと **Referer** ヘッダーを付け、その値を
  楽天ウェブサービスのアプリ設定にある **「許可されたWebサイト」** に登録したURLと一致させる
- アクセスキー（accessKey）はクエリパラメータだけでなく、**ヘッダー** としても送る

これに対応するため、次のように修正しました。

- `src/rakuten_api.py`：`allowed_origin` を受け取り、Origin/Refererヘッダーとして送信するようにした。
  accessKeyもクエリパラメータとヘッダーの両方に含めるようにした
- `config/settings.example.yaml`：`allowed_origin` の初期値として、以前作成したGitHub Pagesの
  案内ページ（`index.html`）のURLを設定した

**重要**：`allowed_origin` の値は、楽天ウェブサービスのアプリ設定画面で実際に登録した
「アプリケーションURL」「許可されたWebサイト」と**1文字も違わずに一致**している必要があります
（`http`と`https`の違い、末尾のスラッシュの有無でも失敗します）。まだ403が出る場合は、
まずここが完全に一致しているかを確認してください。

エラーメッセージには、楽天から返ってきたエラーの説明文（レスポンス本文）を安全な範囲で表示するように
していますが、万一アプリIDやアクセスキーの値がその中に含まれていた場合に備えて、
表示前に自動的にマスク（伏字）処理をしています。

### スマートフォンでも候補を確認できるようにした対応

当初はActionsの「Artifacts（成果物）」としてZIPファイルを保存する形にしていましたが、
スマートフォンではZIPをダウンロード・展開できない（ストレージ容量の都合など）ことがあるため、
GitHub Actionsの実行結果ページに直接表示される「Summary」欄にも候補一覧を表示するようにしました。

- `src/storage.py`：候補一覧をMarkdownとして組み立てる処理を共通化し、
  件数を絞った要約（`build_summary_markdown`）を作れるようにした
- `src/main.py`：実行の最後に、GitHub Actionsが用意する `GITHUB_STEP_SUMMARY` という
  特別なファイルへ、上位10件（`config/settings.yaml`の`summary_item_limit`で変更可）の
  候補一覧を書き込むようにした。これがそのままActionsの実行結果ページの「Summary」欄に表示される
- 自分のパソコンで実行したときは `GITHUB_STEP_SUMMARY` が存在しないため、この処理は何もしない
  （エラーにもならない）
- 全件のデータはこれまでどおりArtifactsからダウンロードできる状態を維持している

## 5. なぜ「広告対象・ポイント倍率・ランキング入賞・SALE・メディア掲載」を除外理由にしないのか

これらは「商品そのものの良し悪し」とは関係のない、販促上の情報だからです。
今回はあくまで「レビュー評価・レビュー件数・売れ行き・テーマとの関連性」という
客観的な指標で商品を選ぶ設計にしています。

## 6. 商品選定・紹介文の質を上げた対応（31件取得に成功した後の改善）

GitHub Actionsで実際に31件の候補取得に成功したあと、次の点を改善しました。

### 商品選定の改善

- `config/settings.example.yaml` の `keywords` を、検索キーワードと
  「掃除／収納／キッチン／時短／暮らし全般」のカテゴリの組み合わせに変更した
  （紹介文の言い回しをカテゴリごとに変えるために使う）
- `ng_keywords`：「福袋」「ランダム」「訳あり」「詰め合わせ」「アソート」など、
  中身が選べない・用途が不明瞭な商品を弾くための簡易チェックを追加した
  （商品名・商品説明にこれらの言葉が含まれていたら除外する）
- `theme_keywords`：「掃除」「収納」「キッチン」「時短」「便利」など、
  テーマに関連する言葉が商品名・商品説明に1つも含まれない場合は、
  テーマから大きく外れているとみなして除外するようにした
  （※この判定方法には問題が見つかり、後の改善で取りやめている。詳細は「7.」を参照）
- 複数のキーワード検索で同じ商品が重複してヒットした場合、同じ実行の中では
  1回だけ候補に含めるようにした（`dedupe.remove_within_run_duplicates`）
- 最終的な候補は、レビュー件数が多い順（＝購入・利用されている実績が多い順）に
  並べ替えてから上位を表示するようにした

> **重複チェックの限界について（正直な注意点）**：`data/posted_items.json`に記録した
> 「実際に投稿した商品」との重複は確実に除外できます。一方で「過去の実行で候補には出たが
> まだ投稿していない商品」を次回以降も除外する仕組みは、今回は実装していません。
> これを実現するにはGitHub Actionsの実行結果を毎回リポジトリにコミットして残す必要があり、
> 書き込み権限の追加や、現在安定して動いているActionsに影響が出るリスクがあるため、
> 今回は見送りました。必要であれば追加で対応できます。

### 紹介文の質の改善

以前は全商品に対してほぼ同じ定型文（決まった3つの文言）を使い回していましたが、
次のように改善しました。

- カテゴリ（掃除／収納／キッチン／時短／暮らし全般）ごとに、書き出しの文章と
  ポイントの言い回しを複数パターン用意し、商品コードに応じて組み合わせを変える
  ことで、同じ文章が続けて使われにくくした
- 紹介文に含めるポイントのうち1つは「レビュー評価○○・○○件」という、
  実際に取得したデータそのものを使い、確認できない効果や性能は書かないようにした
- ハッシュタグは全商品共通のもの（`#楽天ROOM` `#暮らしの便利グッズ`）に加えて、
  カテゴリに応じたタグ（`#掃除グッズ` `#収納` `#キッチン便利グッズ` `#時短アイテム`）を
  自動で付けるようにした
- 紹介文（書き出し文＋箇条書き2〜4個＋ハッシュタグ）を、改行を含む1つの文章ブロック
  としてまとめ、楽天ROOMの紹介文欄にそのままコピペできる形にした

## 7. 商品選定ロジックのさらなる改善（49件取得後、耳かき等の混入を受けて）

GitHub Actionsで49件の候補取得に成功したあと、上位候補に「耳かき」「パスケース」のような
テーマと関連性が薄い商品や、似た用途の商品（トラベルポーチなど）が複数混ざる問題が見つかったため、
次の改善を行いました。

### テーマとの関連性をさらに強化

- `off_theme_keywords`（新規）：「耳かき」「パスケース」「財布」「ネックレス」など、
  ファッション小物・パーソナルケア用品として明らかにテーマから外れるジャンルの言葉を
  商品名・キャッチコピー・商品説明から検出し、強制的に除外するようにした
- 商品説明（`itemCaption`）も新たに取得し、NGワード・オフテーマワードの判定材料に加えた
  （商品タイトルだけでなく、商品説明も使って判定するため）

> **テストで見つけた問題と対応（正直な注意点）**：当初は「テーマ関連語（掃除・収納など）を
> 1つも含まない商品は除外する」という`theme_keywords`による判定も試しましたが、
> オフラインテストで「コードレス充電式ハンディクリーナー」のような、商品名に
> 『時短』等の単語を含まないだけの正当な時短家電まで誤って除外してしまうことが分かりました。
> 検索キーワード自体がすでにテーマに沿って絞り込まれていることもあり、この判定方法は
> 取りやめ、`off_theme_keywords`による「明らかに違うものだけを弾く」方式に一本化しています。

### 類似商品の統合（新規：`src/ranking.py`）

- 同じカテゴリ（掃除／収納／キッチン／時短／暮らし全般）内で商品名の類似度を比較し、
  類似度が一定以上（初期値0.55、`similarity_threshold`で調整可）の商品は
  「用途がほぼ同じ類似商品」とみなして、レビュー評価・レビュー件数が良い方の1件だけを残す
  （例：似たような「折りたたみ収納ボックス」が3つあれば1つに、掃除・収納など別カテゴリの
  商品同士は比較しないので残る）

### 上位10件のカテゴリ分散（新規：`src/ranking.py`）

- レビュー件数順に並べたあと、同じカテゴリが3件（`summary_max_per_category`で調整可）を
  超えて連続で上位に入らないよう選び直す処理を追加した
- 無理に均等にはせず、候補が少ないカテゴリがあれば他のカテゴリで埋める

### 紹介文をより商品固有の内容に

- 商品名・キャッチコピー・商品説明から「マグネット」「吸盤」「折りたたみ」「水切り」
  「ステンレス」など、商品の構造や仕様に関する言葉を検出し、見つかった場合はその特徴を
  紹介文のポイントに反映するようにした（`description_generator.FEATURE_HINTS`）
- 検出できなかった場合のみ、これまでどおりカテゴリ共通の言い回しで補う
- 実際に使用した体験談のような表現や、商品情報から確認できない効果は引き続き書かない
  （検出した言葉も「〜できるタイプ」「〜しやすい設計」など、断定しすぎない表現にしている）

## 8. 紹介文に商品情報にない特徴が混入していた問題への対応

実際にActionsの上位10件を確認したところ、「スープメーカー」の紹介文に「充電式」、
「詰め替えそのまま MINI」や「段ボールストッカー」の紹介文に「ステンレス製」など、
その商品自体には当てはまらない特徴が混入していることが分かりました。

### 原因

商品説明（`itemCaption`）は、配送案内・付属品の説明・他の対応商品との比較など、
その商品自体の特徴ではない文章を含むことが多いです。たとえば「詰め替えそのまま MINI」の
説明文に「ステンレスボトルにも対応」という一文があった場合、これは「対応するボトルの
一例としてステンレス製もある」という意味であり、商品自体がステンレス製という意味では
ありません。以前の実装は商品説明の全文を対象にキーワードを探していたため、こうした
文脈を無視して単語だけを拾ってしまい、誤った特徴を紹介文に書いてしまっていました。

### 1回目の対応（不十分だった）

- `src/description_generator.py`：特徴語を検出する対象を「商品名」と
  「商品説明の最初の一文だけ」に限定した
- 商品名からもカテゴリを補正する仕組み（`refine_category`）を追加した

この対応後にGitHub Actionsを再実行したところ、実際のSummaryには依然として
同じ問題（スープメーカーに「充電式」、詰め替えそのまま MINI・段ボールストッカーに
「ステンレス」、衣類圧縮袋が掃除カテゴリのまま）が残っていました。

### 実データを直接確認して分かった本当の原因

一時的な診断ログを追加してGitHub Actionsを実行し、実際に楽天ウェブサービスから
返ってきた商品名・商品説明を直接確認したところ、次のことが分かりました。

1. **商品説明が句点（。）を含まない仕様一覧形式のことがある**：
   「詰め替えそのまま MINI」の商品説明は
   `素材/材質ポンプ：エラストマー、ポリアセタール、シリコーンゴム、ステンレス、…`
   のように句点が無い一続きの仕様列挙になっており、「最初の一文」のつもりの処理が
   実質的に説明文全体を拾ってしまっていました
2. **ショップの入力ミスと見られる、無関係な説明文が入っていることがある**：
   「スープメーカー」の商品説明の冒頭は
   `ロングヒット！人気アイテム 片胸・両胸派も！充電式でラクラク搾乳…`
   という、明らかに別商品（搾乳機）の説明文でした。商品名には「充電式」という
   言葉は一切含まれていません
3. **カテゴリ判定が「1語でも一致すれば元のカテゴリのまま」だった**：
   「衣類圧縮袋」の商品名には「掃除機**不要**」という言葉が含まれており、
   この『掃除』の1語だけで「掃除」カテゴリの判定が維持されてしまっていました
   （商品名には「収納」「圧縮袋」「ケース」「ボックス」など、収納カテゴリの
   言葉の方が多く含まれているにもかかわらず）

### 最終的な対応

- `src/description_generator.py`：特徴語の検出を**商品説明を一切使わず、
  商品名だけ**に限定した。商品説明はショップによって書式や品質にばらつきが
  大きく、簡単な文分割では安全に扱えないと判断したため
- `refine_category()`を、単純な「1語でも一致」判定から、**カテゴリごとの
  一致キーワード数を数えて最多のカテゴリを採用するスコア方式**に変更した
  （同点の場合は元のカテゴリを優先）
- 「透明」という特徴語は、収納ケースなどの文脈以外（今回はテープ）にも
  一致してしまい、「中身が見えてわかりやすいタイプ」という表現が不自然になる
  ケースがあったため、検出リストから削除した
- `tests/test_description_generator.py`：**実際にGitHub Actionsの本番実行で
  取得した商品名・商品説明をそのままテストデータとして使用**し、上記の問題が
  再発しないことを確認できるようにした
  （`python -m unittest tests.test_description_generator -v` で実行できる）

なお、この対応は「確実に読み取れる特徴だけを使う」という方向への変更のため、
今まで以上に「特徴が見つからずカテゴリ共通の言い回しになる商品」が増える可能性があります。
これは条件（無理に特徴を作らない）を優先した結果であり、意図した挙動です。

## 9. カテゴリ判定のキーワードを見直し（依然として掃除カテゴリに寄っていた問題）

「8.」の対応後にGitHub Actionsを再実行し、実際のSummaryを確認したところ、
特徴の誤抽出は解消していましたが、カテゴリ判定はまだ不正確でした。

- 「衣類圧縮袋」「詰め替えそのまま MINI」「tower マグネットバスルームフック」が、
  いずれも本来「収納」であるべきところ「掃除」カテゴリ（`#掃除グッズ`）のままだった

### 原因

`refine_category()`のスコア方式自体は正しく動いていましたが、
`CATEGORY_NAME_KEYWORDS`のキーワード選定に問題がありました。

- 「掃除」カテゴリに含めていた**「掃除」という1語そのもの**が広すぎた。
  「掃除機**不要**」（衣類圧縮袋によくある宣伝文句）や「掃除用具」「掃除道具」
  （tower マグネットバスルームフックの商品名にあった、便利グッズ全般を指す
  一般的な表現）にまで一致してしまい、実際には掃除道具ではない商品の
  スコアを底上げしてしまっていました
- 「収納」カテゴリのキーワードに「フック」「ホルダー」「吊り下げ」
  「浮かせる収納」「ポーチ」「収納袋」が含まれておらず、実際には収納用品なのに
  スコアで「収納」が「掃除」に勝てないことがありました

### 対応

- `CATEGORY_NAME_KEYWORDS["掃除"]`から曖昧な「掃除」を削除し、商品自体が
  掃除道具だと言い切れる具体的な言葉（「クリーナー」「モップ」「ワイパー」
  「洗剤」「ブラシ」「雑巾」「掃除機」）だけに絞った
- `CATEGORY_NAME_KEYWORDS["収納"]`に「収納袋」「ポーチ」「フック」「ホルダー」
  「吊り下げ」「浮かせる収納」を追加した
- `NEGATED_PHRASES`（新規）：「掃除機不要」のように、キーワードを含んでいても
  実際には逆の意味を表す言い回しを、判定前に商品名から取り除くようにした
- `tests/test_description_generator.py`：実際にGitHub Actionsで「掃除」カテゴリの
  ままになっていた3商品（衣類圧縮袋・詰め替えそのまま MINI・
  tower マグネットバスルームフック）すべてが「収納」になることを確認するテストと、
  「掃除機不要」を含む商品が掃除カテゴリと判定されないこと、逆に実際の掃除機
  （コードレス掃除機など）は引き続き掃除カテゴリと判定されることを確認する
  テストを追加した（22テストすべて成功）

## 10. 特徴の言い回しをカテゴリに応じて変える（「大容量」が調理家電にも収納向けの表現で出ていた問題）

Run #12のSummaryを確認したところ、カテゴリ判定は改善していましたが、
「ノンフライヤー 4.2L」（カテゴリ：時短）の紹介文に
「たっぷり**収納できる**大容量タイプ」という、収納用品向けの表現がそのまま
使われており、調理家電としては不自然でした。

### 原因

`FEATURE_HINTS`の「大容量」という言い回しは、商品のカテゴリに関わらず
常に同じ「たっぷり収納できる大容量タイプ」という固定文言を使っていました。
「大容量」は収納用品・調理家電・かばん類などジャンルを問わず商品名によく
登場する言葉なので、カテゴリに関係なく同じ言い回しを使うと不自然になる
ケースがありました（同様に「吊り下げ」も「吊り下げて収納できるタイプ」
固定だったため、収納以外のカテゴリで使われると不自然になり得ました）。

### 対応

- `src/description_generator.py`：`FEATURE_HINTS`の値を、固定の文言（文字列）
  だけでなく、カテゴリ名をキーにした言い回しの辞書も指定できるように拡張した
  （`_resolve_hint_phrase`でカテゴリに応じた文言を選ぶ）
- 「大容量」の言い回しをカテゴリ別に用意した：
  収納＝「たっぷり収納できる大容量タイプ」、キッチン＝「一度にたっぷり調理
  しやすい容量」、時短＝「一度にたっぷり使える大容量タイプ」、掃除＝
  「一度にたっぷり集められる大容量タイプ」、それ以外＝「たっぷり使える
  大容量タイプ」
- 「吊り下げ」も同様に、収納以外では「収納」という言葉を使わない
  「吊り下げて使えるタイプ」に変更した
- `tests/test_description_generator.py`：実際の「ノンフライヤー 4.2L」の
  商品名を使い、紹介文に「収納できる大容量タイプ」は出ないこと、
  「収納」という言葉自体が含まれないことを確認するテストを追加した
  （23テストすべて成功）

## 11. 紹介文に絵文字を追加（見やすさ・親しみやすさの向上）

文字だけの紹介文よりも見やすく親しみやすくするため、絵文字を追加した。
このブランチ（`claude/rakuten-room-emoji-descriptions`）は、これまでの
`claude/rakuten-room-automation-dulzvm`ブランチから分岐した新しいブランチで
作業している。

### 方針

- 1投稿あたりの絵文字は3〜6個程度（導入文1個＋箇条書き2〜3個＋レビュー行1個の
  合計4個が基本）
- 導入文の先頭にカテゴリに合った絵文字を1つ（`CATEGORY_EMOJIS`から選ぶ）
- 箇条書きの先頭にも、その内容に合う絵文字を1つずつ付ける
  （`FEATURE_HINTS`・`POINT_VARIANTS`のそれぞれに絵文字を対応付けた）
- レビュー実績の行には`⭐`を固定で使う
- ハッシュタグ行には絵文字を付けない
- 絵文字が内容と無関係に情報を付け足さないよう、絵文字は「すでに文章として
  決まった特徴・カテゴリ」に対する飾りとしてのみ使い、絵文字をきっかけに
  新しい特徴を書き足すことはしない

### 実装

- `src/description_generator.py`：
  - `CATEGORY_EMOJIS`（新規）：カテゴリごとの絵文字候補（例：収納＝
    🧺🧲🧴📦✨、掃除＝🧹🧽✨、キッチン＝🍳🥣🥄✨、時短＝⏱️⚡🍳✨、
    暮らし全般＝🏠✨💡）
  - `POINT_VARIANTS`の各文言に絵文字を対応付け（`(テキスト, 絵文字)`のタプルに変更）
  - `FEATURE_HINTS`の各特徴にも絵文字を対応付け（3要素目として追加。「大容量」
    のようにカテゴリで文言が変わるものは絵文字もカテゴリ別の辞書にした）
  - `_pick_intro_emoji()`（新規）：導入文の絵文字を、箇条書きで使う絵文字と
    被らないようカテゴリの候補からローテーションで選ぶ
    （「同じ絵文字を不自然に連続使用しない」ための配慮）
- `tests/test_description_generator.py`：`EmojiFormatTest`を追加し、
  絵文字の合計数が3〜6個の範囲であること、導入文がカテゴリの絵文字で
  始まること、レビュー行が`⭐`で始まること、ハッシュタグ行に絵文字が
  付かないこと、実際の商品（towerマグネットラック・ノンフライヤー）で
  カテゴリに応じた絵文字が正しく選ばれることを確認した（30テストすべて成功）

既存のカテゴリ判定・特徴抽出・レビュー表記のロジックそのものは変更していない
（絵文字を追加しただけで、判定結果や文言は変わらない）。

## 12. 紹介文を「導入文＋箇条書き」から自然な文章形式に変更

前の11の形式（導入文1行＋箇条書き2〜3行＋レビュー行＋ハッシュタグ行）は、
実際にSummaryで見ると機械的で押し売り感がある、という指摘を受け、
箇条書きを使わない自然な文章形式に作り直した。このブランチ
（`claude/rakuten-room-emoji-descriptions`）の上でそのまま作業している。

### 方針（新しい生成ルール）

- 箇条書き「・」は使わない
- 2〜3文程度の短く読みやすい紹介文にする
- 商品名や特徴に合わせて毎回文章を変える（カテゴリだけで文章を決めない）
- 商品ページ（商品名）から確認できる特徴を自然に文章へ組み込む
- 「〜できそう」「〜に便利そう」「〜したい人におすすめ」など、実際に
  使用していない立場でも不自然にならない表現を使う。「使ってみました」
  「買ってよかった」など、使用したと誤解される表現は使わない
- 絵文字は文末など意味の合う場所に自然に入れる。各行の先頭へ機械的に
  付けない。1投稿につき2〜4個程度、😊✨♪などを使い柔らかい雰囲気にする
- レビュー評価・レビュー件数は紹介文の本文には原則含めない
  （候補一覧には別項目として表示されるため、本文は文章の自然さを優先する）
- ハッシュタグは3〜5個程度、商品に合ったものを自動生成する。
  「#暮らしの便利グッズ」は基本的に入れる。ハッシュタグに絵文字は付けない

### 実装

- `src/description_generator.py`：
  - `FEATURE_HINTS`を`FEATURE_CLAUSES`に置き換えた。値は「タイプです」の
    ような体言止めではなく、「マグネットで浮かせて設置できる」のように
    そのまま名詞（カテゴリ名）の前に続けられる形（連体修飾の節）にした
  - `POINT_VARIANTS`（箇条書き用の断片）を廃止し、代わりに1文目
    （`OPENING_FALLBACK_SENTENCES`・特徴が見つかった場合は`FEATURE_CLAUSES`
    から組み立て）、2文目（`BENEFIT_SENTENCES`、おすすめ・メリットの
    やわらかい言い回し）、3文目（`CLOSING_SENTENCES`、付くこともある
    締めの一文）という、完結した文単位のバリエーションに変更した
  - `generate_description()`：商品コード（無ければ商品名）から作る
    `seed`値で、2文目・3文目の有無・絵文字の選び方をローテーションし、
    同じ商品なら毎回同じ文章になる（再現性がある）が、商品が違えば
    自然にバリエーションが出るようにした
  - `_dedupe_adjacent_emojis()`（新規）：隣り合う文で同じ絵文字が
    続かないよう調整する
  - 1文目には、楽天ROOMでよく見る「文末に絵文字を2つ重ねる」表現
    （例：🛁✨）を一定の確率で加えている。追加する絵文字は、その行だけで
    なく紹介文全体で既に使われている絵文字を除外して選ぶ（開発中に、
    他の文の絵文字と重複してしまう不具合が見つかったため、文章全体で
    重複を避けるよう修正した）
  - レビュー評価・件数を本文に含める処理（`REVIEW_EMOJI`・レビュー行の
    組み立て）を削除した
  - `HASHTAG_BY_CATEGORY`の「暮らし全般」を、基本ハッシュタグの
    「#暮らしの便利グッズ」と重複しない「#暮らし雑貨」に変更した
    （重複していると、サブトピックに一致しない商品でハッシュタグが
    2個しか付かず、「3〜5個程度」のルールを満たせなくなるため）
- `config/settings.example.yaml` / `src/main.py`：紹介文の例に
  「#楽天ROOM」が含まれていなかったため、`default_hashtags`から
  「#楽天ROOM」を外し「#暮らしの便利グッズ」のみにした
- `tests/test_description_generator.py`：箇条書き・レビュー行を前提にした
  アサーションをすべて書き換え、新しいルール（箇条書きなし、文の数が
  2〜3、絵文字数が2〜4、レビュー数値が本文に含まれない、ハッシュタグ数が
  3〜5）を確認するテストに変更した。既存の実データ回帰テスト（衣類圧縮袋・
  詰め替えそのままMINI・towerマグネットラック／フック・ノンフライヤー等）
  はそのまま流用し、新しい文章形式でも同じ問題が再発しないことを確認した。
  また、多数の商品名・全カテゴリの組み合わせでフォーマットのルールが
  常に守られることを確認する一括テストも追加した（37テストすべて成功）

カテゴリ判定（`refine_category`）・特徴の検出対象を商品名だけに限定する
ロジックは変更していない。

## 13. 商品名の単語だけで特徴を決めつけない対応（用途と食い違う紹介文の修正）

「12.」の対応後にGitHub Actionsを実行し、実際のSummaryを確認したところ、
文章の形式は改善していたが、次のように「商品名に含まれる単語」と
「商品全体の用途」が食い違う紹介文が見つかった。

- 三角コーナー（生ゴミの水切り用）の商品名に「吸盤」が含まれ、
  紹介文が「吸盤で好きな場所に取り付けられる」になっていた
- 味噌マドラーの商品名に「ステンレス」が含まれ、紹介文が
  「サビに強いキッチングッズです」になっていた
- ドアストッパーの商品名に「マグネット」が含まれ、紹介文が
  「マグネットで浮かせて設置できる」（収納用品向けの表現）になっていた

### 原因

`FEATURE_CLAUSES`（構造・仕様の単語一致）で見つかった特徴を、そのまま
1文目（紹介文の主役）にしていたことが原因。楽天の商品名はSEO対策で
多くの単語が詰め込まれていることが多く、「単語が商品名に含まれる」ことは
「それが商品全体の用途である」ことを意味しない。特に「マグネット」
「吸盤」「ステンレス」のような構造・素材の単語は、商品の主な用途とは
無関係な付属的な特徴を指していることがある。

### 対応

- `src/description_generator.py`：
  - `PRODUCT_TYPE_HINTS`（新規）：商品名から「この商品が具体的に何であるか」
    がほぼ確実に分かる場合に使う、商品全体の用途に沿った1文目の一覧。
    `FEATURE_CLAUSES`（構造・仕様の単語一致）より必ず先に判定する
    （三角コーナー・ドアストッパー・マドラーを追加）
  - 1文目（`_build_sentence1`）は、`PRODUCT_TYPE_HINTS`に一致しなければ
    必ず`OPENING_FALLBACK_SENTENCES`（カテゴリ共通の用途ベースの言い回し）
    を使うようにし、`FEATURE_CLAUSES`から1文目を組み立てる処理を廃止した
    （構造・仕様の単語だけを根拠に1文目を作らないようにするため）
  - `FEATURE_CLAUSES`で見つかった特徴は、`PRODUCT_TYPE_HINTS`で商品の種類が
    特定できなかった場合に限り、2文目に「〜なので、」という**理由**として
    添えるだけにした（`_build_sentence2`）。特徴を紹介文から無くすのではなく、
    「主役にしすぎない」形で残している
  - `FEATURE_CLAUSES`から「ステンレス→サビに強い」を削除した。素材だけを
    述べる表現は、商品全体の用途（使うと何がラクになるか）に繋がりにくく、
    紹介文の主題として不自然になりやすいため
  - 「吸盤」の絵文字を、磁石を連想させる🧲から、汎用的な✨に変更した
    （吸盤は磁石ではないため）
  - `BENEFIT_SENTENCES`・`CLOSING_SENTENCES`のバリエーションを各2個ずつ
    追加し、同じ定型文が連続しにくくした
- `tests/test_description_generator.py`：`ProductTypeMismatchRegressionTest`
  （新規）を追加し、三角コーナー・味噌マドラー・ドアストッパーを

## 14. 紹介文を「共感型」の6ブロック構成に変更

「13.」の対応後にGitHub Actionsを実行し、実際のSummaryを確認したところ、
商品との不一致は改善していたが、文章が抽象的すぎる（「気になる場面で活躍
してくれそうです」等、商品を見なくても使える文章）という指摘を受けた。
一度その対応に着手したが、最終的には方向性そのものを変更し、楽天ROOMで
読んだ人が「これ便利そう」「欲しい」と感じやすい、共感型の紹介文に
作り直した。

### 新しい構成

1文〜2文の短い文章ではなく、次の6ブロック構成にした（各ブロックは空行で区切る）。

```
① 絵文字＋短いキャッチコピー（例：🏠 リモコンの置き場所、決まってる？✨）
② 使う前にありがちな悩み・あるある（1〜2文、「〜って意外と面倒…😅」等）
③ 商品がどう解決してくれそうか（例：そんな小さなストレスを減らしてくれそうな収納ラック◎）
④ ✔️を使ったメリット3項目（✔️ リモコンの定位置を作れる 等）
⑤ 自然な一言の締め（商品ごとに複数パターンから選ぶ）
⑥ ハッシュタグ3〜5個
```

### 実装

- `src/description_generator.py`：
  - `_PostTemplate`（新規）：①〜⑤の文章一式（キャッチコピー・絵文字・悩み・
    解決・メリット2項目・締めの複数パターン）を持つ入れ物
  - `PRODUCT_TYPE_TEMPLATES`（`PRODUCT_TYPE_HINTS`を全面的に置き換え）：
    商品名から具体的な商品タイプが分かる場合に使う、①〜⑤すべてを含む
    テンプレート一覧。ロボット掃除機・スープメーカー・ノンフライヤー・
    フライパン・リモコンラック・水切りボウル・シーツハンガー・
    ドライヤースタンド等、よくある商品タイプを収録した
  - `GENERIC_TEMPLATES`（`OPENING_FALLBACK_SENTENCES`・`BENEFIT_SENTENCES`・
    `CLOSING_SENTENCES`を統合・置き換え）：商品タイプが特定できない場合に
    使う、カテゴリ（掃除／収納／キッチン／時短／暮らし全般）共通の
    安全なテンプレート
  - ✔️メリットの3項目のうち、2項目はテンプレートの安全な内容を使い、
    残り1項目は商品名から`FEATURE_CLAUSES`（マグネット式・折りたたみ式等）
    が読み取れればそれを使う（読み取れなければテンプレートの安全な
    言い回しで補う）。これにより、「13.」で対応した「商品名の単語だけで
    決めつけない」考え方（商品全体の用途を主役にし、構造・仕様の特徴は
    補足として添える）を新しい構成でも引き継いでいる
  - `LOCATION_HINTS`・`_resolve_location()`は維持し、`GENERIC_TEMPLATES`の
    「収納」テンプレートでは`{location}`のプレースホルダーを使って、
    商品を使う場所（浴室・キッチン・玄関等）が分かればその言葉に、
    分からなければ「身の回り」に置き換わるようにした
  - `LOCATION_TOPIC_EMOJI`（新規）：場所が分かる場合、①の先頭の絵文字も
    場所に合わせて変える（浴室用品なら🛁、洗面所用品なら🪞等）
  - レビュー評価・件数に加えて、**価格**も紹介文に含めないようにした
    （今回追加されたルール）
  - `CATEGORY_EMOJIS`・`_dedupe_adjacent_emojis`等、絵文字をランダムに
    ローテーションする仕組みは不要になったため削除した（✨😅◎✔️☺️は
    構成上固定の飾りとして使い、先頭の絵文字だけが商品タイプ・場所に
    応じて変わる、という単純な仕組みにした）
- `tests/test_description_generator.py`：6ブロック構成（①〜⑥それぞれの
  始まり・終わり方）を確認するテストに全面的に書き換えた。価格が本文に
  含まれないこと、商品名をそのまま長く転載しないことを確認するテストを
  新たに追加し、既存の実データ回帰テスト（衣類圧縮袋・詰め替えそのまま
  MINI・towerマグネットラック／フック・スープメーカー・ノンフライヤー等）
  もこの構成に合わせて更新した（44テストすべて成功）

カテゴリ判定（`refine_category`）・特徴の検出対象を商品名だけに限定する
ロジック・ハッシュタグの組み立てロジックは変更していない。

## 15. 「確認できない性能を推測しない」ルールの強化

「14.」の6ブロック構成後にGitHub Actionsを実行し、実際のSummaryを確認した
ところ、文章の雰囲気・構成は理想に近かったが、次のように商品名・取得データ
からは確認できない性能・用途・操作方法を推測してしまっている例が見つかった。

- ドアストッパー：「マグネットで浮かせて設置できる」→マグネットで
  取り付けられることは確認できるが、「浮かせて設置」は収納用品向けの
  用途で、ドアストッパーの用途と合わない
- ノンフライヤー：「油を使わずに揚げ物を作れる」→「油不使用」と明示
  されていないのに、油ゼロを断定していた
- フライパン：「焦げつきやすいフライパンだと」「後片付けしやすい」→
  商品情報に明示されていない性能を悩み・メリットとして書いていた
- ロボット掃除機：「スイッチひとつで」→商品名・データに明示されていない
  操作方法を勝手に限定していた

### 対応

- `src/description_generator.py`：
  - `FEATURE_CLAUSES`の「マグネット」の文言を「マグネットで浮かせて設置
    できる」から、商品名から確認できる事実だけの「マグネットで取り付け
    られる」に変更した。これは✔️メリットの3項目目として、ドアストッパー・
    収納ラックなど商品タイプを問わず使われるため、1箇所の修正で
    全体に反映される
  - `PRODUCT_TYPE_TEMPLATES`の該当箇所を修正：
    - ノンフライヤー：「油を使わずに」→「油を控えて」に変更し、
      「揚げ物風の調理がしやすい」「油の後片付けを減らしやすい」という、
      商品情報から安全に言える表現にした
    - フライパン：「焦げつきやすいフライパンだと」という悩みを、
      商品固有の性能を前提にしない「毎日使うものだから、扱いやすさや
      使い勝手が気になりますよね」という一般的な悩みに変更した。
      「後片付けもしやすくなりそう」も「毎日の調理に取り入れやすそう」
      に変更した
    - ロボット掃除機：「スイッチひとつで床掃除をおまかせできる」から
      「スイッチひとつで」という操作方法の限定を外し、「床掃除を
      おまかせしやすい」に変更した
  - 上記以外のテンプレート・`GENERIC_TEMPLATES`・`FEATURE_CLAUSES`
    （大容量・充電式等）についても、「できる」という言い切りの表現を
    「できそう」「しやすい」といった、ためらいのある言い回しに揃える
    軽い見直しを行った（断定が危険な場合はやわらかい表現にする、という
    ルールの徹底）
  - モジュールの docstring（生成ルール）に「商品名、APIから取得した情報、
    明示された仕様だけを根拠にする」「悩み（②）も、商品から自然に想定
    できる一般的な悩みだけにする」という条件を明記した
- `tests/test_description_generator.py`：報告された4パターン
  （ドアストッパーのマグネット文言、ノンフライヤーの油ゼロ断定、
  フライパンの未確認性能、ロボット掃除機の操作方法限定）それぞれについて、
  該当する誤った表現が紹介文に出てこないことを確認する回帰テストを追加した
  （47テストすべて成功）

共感型の6ブロック構成・現在のトーン、ハッシュタグ3〜5個のルールは
変更していない。

- 商品ページ側に「ROOMで投稿」が表示されない場合（レイアウトや商品の

- 従来あった「楽天商品ページを開く」ボタンは、上記の「② 楽天市場を開く」
  ボタンと開き先（`item_url`）が完全に同じため、重複を避けて統合し廃止した。

## 18. 毎日の候補10件を「暮らしの便利グッズ5件」＋「消耗品・飲料5件」に分ける

これまで毎日の投稿候補10件は、レビュー実績順に並べたうえでカテゴリの偏りだけを
抑える1つの枠から選んでいた。今回、暮らしの便利グッズだけでなく、洗剤・
キッチン消耗品・トイレットペーパーなどの日用品や、水・お茶・ジュースといった
飲料も投稿できるようにするため、選定を「暮らしの便利グッズ」枠と
「消耗品・飲料」枠の2つに分け、それぞれ5件ずつ（合計最大10件）選ぶ方式に変更した。

### 仕組み

- `config/settings.yaml`の`keywords`の各エントリに`group`
  （`convenience`=暮らしの便利グッズ／`consumable`=消耗品・飲料）を追加した。
  既存の5キーワード（掃除・収納・キッチン・時短・暮らし全般）は
  `group: convenience`のまま、内容・検索ロジックは変更していない。
  新たに12キーワード（洗剤・キッチン消耗品・日用品・水・お茶・ジュースの
  各2件）を`group: consumable`として追加した。
- `src/main.py`のフェーズ1（検索・条件判定・重複チェック）は、
  レビュー条件・NGワード・テーマ除外・重複チェックのロジック自体は
  一切変更せず、各商品に`_group`（枠）と`_display_group`
  （投稿ページに表示する「便利グッズ／消耗品／飲料」の小さな表示）を
  タグ付けするようにしただけ。「消耗品・飲料」枠は検索キーワード自体が
  商品種別そのもの（例：「洗濯洗剤」というキーワードで検索した商品は
  確実に洗剤）なので、便利グッズ枠のような商品名からのカテゴリ補正
  （`refine_category`）は行わない。補正ロジックのキーワード一覧は
  便利グッズ向けに作られており、そのまま適用すると例えば洗剤の商品名に
  ある「洗剤」の一語で掃除カテゴリに誤って補正されてしまうため。
- 飲料カテゴリ（水／お茶／ジュース）の商品だけ、`ng_keywords`等とは別に
  新設した`alcohol_keywords`（ビール・チューハイ・ワイン等）で
  アルコール飲料を除外する（`filters.filter_by_alcohol_keywords`）。
- 飲料カテゴリの商品は、`ranking.sort_consumable_items`で「24本」
  「ケース」「まとめ買い」のような複数本セットを示す表記
  （`ranking.is_multipack`）を単品より優先して並べる。飲料以外の
  消耗品（洗剤・キッチン消耗品・日用品）は、これまでどおりレビュー実績
  だけで並べる。
- フェーズ2（類似商品の統合）・フェーズ3（紹介文生成）は既存のロジックの
  ままで、`_group`によって処理を分けていない（カテゴリが便利グッズ・
  消耗品・飲料の間で重複しないため、これまでの仕組みがそのまま使える）。
- フェーズ4（上位候補の選定）だけを、`ranking.sort_by_quality` +
  `ranking.diversify_top`の単純な呼び出しから、新設の

  その不足分をもう片方の枠の残り候補（品質順）から補充する。合計は
  常に10件（`convenience_target + consumable_target`）を超えない。

### 紹介文

## 19. 投稿済み履歴による重複防止の強化

これまでの重複チェックは、`data/posted_items.json`の`posted_item_codes`
（商品コードだけの一覧）と、商品コードが完全一致するかどうかだけで
判定していた。今回、投稿済み履歴をより詳しい情報（商品URL・商品名・投稿日時
・カテゴリ）を持つ形に拡張し、商品コードが取れない・変わってしまった場合でも
商品URLで一致すれば重複とみなせるようにした。あわせて、スマホ投稿ページで
「投稿済みにする」にした商品を、履歴へ取り込みやすい形でコピーできるように
した。

### 履歴ファイルの形式（後方互換）

```json
{
  "posted_item_codes": ["shop:item001", ...],
  "posted_items": [
    {
      "item_code": "shop:item001",
      "item_url": "https://item.rakuten.co.jp/shop/item001/",
      "product_name": "...",
      "posted_at": "2026-09-14T06:30:00+00:00",
      "category": "収納"
    },
    ...
  ]
}
```

`posted_item_codes`は後方互換のために残してあり、`posted_items`から
自動的に再計算される（`src/dedupe.py`の`_save_posted_items`）。以前の
形式（`posted_item_codes`のみのファイル）もそのまま読み込める
（`load_posted_items`が`item_code`だけの簡易レコードに変換する）ため、
既存のファイル・過去のGitHub Actions実行との互換性は壊れていない。

### 重複判定の優先順位

`src/dedupe.py`の`is_posted`が、次の順で商品が投稿済みかどうかを判定する。

1. `item_code`（安定した商品ID）が履歴に登録されている商品コードと一致するか
2. 商品URLを正規化（クエリ文字列・フラグメント・末尾スラッシュの違いを
   無視）した上で、履歴に登録されている商品URLと一致するか

`src/main.py`のフェーズ1（キーワードごとの検索直後、既存のレビュー条件・
NGワード・テーマ除外・アルコール除外・耐久アクセサリ除外と同じ並びの
タイミング）でこの判定を使って候補から除外する。除外は選定（フェーズ4の
`select_balanced_top`）より前に行われるため、既存の「片方の枠が5件に
満たない場合はもう片方から補充する」という仕組みがそのまま働き、投稿済み
商品を除外したあとも可能な範囲で合計10件・5+5のバランスを維持できる
（`select_balanced_top`自体は変更していない）。

### スマホ投稿ページの「投稿済みデータをコピー」

GitHub Pagesは静的サイトのため、ブラウザからGitHubリポジトリへ直接
書き戻す仕組みは（意図的に）追加していない。代わりに、「投稿済みにする」で
登録した商品の情報（商品コード・商品URL・商品名・投稿日時）をlocalStorage
にそのまま保持しておき、ページ上部の「投稿済みデータをコピー」ボタンで
`data/posted_items.json`にそのまま取り込める形式のJSONとしてクリップボードに
コピーできるようにした。以前のバージョン（真偽値のみ保存）で登録された
商品が残っていても、表示中の候補データから商品URL・商品名を補って
コピーできるようにしている（後方互換）。

### 取り込み用の補助スクリプト・関数分離

コピーしたJSON（またはそれ以外の方法で用意した、過去の投稿済み商品一覧）を
履歴に取り込むため、`python -m src.import_posted_items <ファイル>`を追加した。
履歴への書き込み処理自体は`dedupe.append_posted_items`という1つの関数に
分離してあり、`import_posted_items`はその薄いCLIラッパーに過ぎない。
将来、別の手段（ROOM側の何らかの正式なエクスポート機能等）で履歴を
自動更新できるようになった場合も、この関数を呼び出すだけで済む設計に
している。`append_posted_items`は、履歴・追加しようとしているリスト自身の
両方について、商品コードまたは商品URLの重複を確認してから追記するため、
同じ商品を誤って二重登録することはない。

このスクリプトでは楽天ROOMへのログイン・Cookie・セッション情報を使った
自動取得・自動投稿は一切行っていない。あくまで、人間が用意した（またはROOMの
公式画面からコピーした）商品一覧を取り込むだけの処理である。

### GitHub Actions Summaryへの表示

毎日の実行結果に、投稿済み履歴による重複防止の状況
（`storage.build_posted_history_summary_markdown`）を追加した。

- 投稿済み履歴によって除外した件数
- 今回選ばれた新規候補の件数
- 現在の投稿済み履歴の総数

これらは、既存の候補一覧表示（`storage.build_summary_markdown`）の
直前に表示される。既存のSummary表示・Artifact保存の仕組みは変更していない。

## 20. item_code・URLが無い過去投稿のための、商品名ベースの補助重複判定

楽天ROOMへの過去の投稿（81件）を重複防止に活かしたいが、投稿時点の
`item_code`や商品URLを記録していない場合がある。そこで、`item_code`・
商品URLでの判定（既存・変更なし）に加えて、商品名の正規化後の完全一致による
補助的な重複判定を追加した。優先順位は次のとおり（`dedupe.match_posted_reason`）。

1. `item_code`が一致するか
2. 正規化した商品URLが一致するか（既存の判定、変更なし）
3. 正規化した商品名が一致するか（今回追加。1・2より優先度を下げてある）

### 商品名の正規化（`dedupe.normalize_product_name`）

次の処理を順に行う。

1. Unicode正規化（NFKC）——全角/半角の違い（英数字・記号・スペース）を
   吸収する。
2. 絵文字の除去（代表的な絵文字のUnicode範囲を対象にした簡易的な除去）。
3. 販売文言・宣伝表現の除去——「送料無料」「ポイント◯倍」「ランキング」
   「公式」「限定」「レビュー特典」「ギフト」「SNSで(も)話題」「365日発送」
   「クーポン」「セール」を、指定された言葉・パターンだけ取り除く（依頼に
   挙げられた例のとおりで、網羅的な広告文言辞書は作っていない）。
4. 装飾記号（【】《》〈〉「」『』［］()（）!！?？・*＊#＃★☆）の除去——
   記号「だけ」を取り除き、**中身の文字列は消さない**（例：「《 山崎実業
   マグネットバスルームラック タワー ワイド 》」→「 山崎実業
   マグネットバスルームラック タワー ワイド 」）。
5. 英字の小文字化。
6. 連続する空白の1つのスペースへの圧縮・前後の空白除去。

ブランド名・シリーズ名・サイズ・容量・本数・個数・型番・S/M/L・
ワイド/ラージ・◯個セットなどは、上記のどの処理でも対象にしていないため、
そのまま残る。

### 誤判定防止（あいまい一致にしない）

`match_posted_reason`での商品名判定は、正規化後の文字列が**完全一致**した
場合だけ「投稿済み」とみなす。部分一致・類似度判定（`ranking.py`の
`deduplicate_similar_items`が使っている`difflib.SequenceMatcher`）は
使っていない。理由は、似ている別商品を誤って除外しないため。

- 「tower マグネットバスルームラック タワー ワイド」と
  「tower マグネットバスルームラック タワー ラージ」→ 正規化後も末尾の
  「ワイド」「ラージ」が異なるため一致せず、別商品として扱われる。
- 「冷凍ごはん容器 1個」と「冷凍ごはん容器 5個セット」→ 同様に「1個」
  「5個セット」が異なるため一致せず、別商品として扱われる。

また、正規化した結果が空文字になった商品名同士（絵文字だけの商品名等）を
誤って「両方空文字だから一致」としないよう、空文字は常に不一致として扱う。

### 過去投稿の初期登録

`item_code`・商品URLが分からない過去投稿も、商品名だけで
`data/posted_items.json`に登録できるようにした（`dedupe.append_posted_items`
は、`item_code`・商品URL・商品名のいずれか1つでもあれば受け付ける。すべて
無い場合だけ登録を拒否する）。

```json
{
  "product_name": "マーナ シートケース",
  "item_code": null,
  "item_url": null,
  "posted_at": null,
  "category": "過去投稿"
}
```

`item_code`・商品URL・`posted_at`に`null`が入っていても、空文字として
安全に扱う（`dedupe._clean_str`）。取り込みは`src/import_posted_items.py`
（変更なし、既存の一括取り込みスクリプトがそのまま使える）。

過去投稿をまとめて登録するための下書き用として、`data/past_posted_items_seed.json`
を新設した。このファイル自体は検索時の本番履歴（`data/posted_items.json`）
としては読み込まれない。あくまで`import_posted_items`で取り込むための
一時置き場で、商品名の一覧を追記してから

```bash
python -m src.import_posted_items data/past_posted_items_seed.json
```

を実行すると、`data/posted_items.json`へ安全に（重複を避けて）取り込まれる。

## 21. スクリーンショットからしか確認できない過去投稿のための、match_keywords補助判定

過去のROOM投稿81件の中には、商品名すら正確に思い出せず、スクリーンショットの
一部（ブランド名や特徴的な言葉）からしか特定できないものがある。そこで、
既存の判定（item_code→URL→商品名の完全一致、変更なし）に加えて、4番目の
補助判定として`match_keywords`を追加した。

### 優先順位

`dedupe.match_posted_reason`の判定順位は次のとおり（1〜3は変更なし）。

1. `item_code`が一致するか
2. 正規化した商品URLが一致するか
3. 正規化した商品名が完全一致するか
4. `match_keywords`（登録した特徴語）がすべて商品名に含まれるか（今回追加。
   他の3つより優先度を下げてある）

### match_keywordsの判定（`dedupe.match_all_keywords`）

候補の商品名・登録したキーワードの両方をNFKC正規化・小文字化した上で、
登録された`match_keywords`の**全語**が商品名に含まれている場合だけ一致と
みなす（AND判定）。`normalize_product_name`（3の判定で使う正規化）と違い、
販売文言・装飾記号の除去は行わない——キーワード自体を人間が選んでいるため、
広告文言が紛れ込む心配がなく、余計な処理をしない方が誤判定のリスクが低いと
判断した。

```python
match_all_keywords("tower 《 山崎実業 マグネットバスルームラック タワー ワイド 》",
                    ["山崎実業", "tower", "マグネットバスルームラック", "ワイド"])
# → True（全語を含む）

match_all_keywords("tower マグネットバスルームラック タワー ラージ",
                    ["山崎実業", "tower", "マグネットバスルームラック", "ワイド"])
# → False（「ワイド」を含まない「ラージ」なので不一致）
```

### 誤判定防止（1語だけの登録を無効化）

`["tower"]`や`["マーナ"]`のような1語だけの登録は、無関係な商品まで
巻き込んでしまうリスクが高い。そのため、`_MIN_MATCH_KEYWORDS = 2`未満の
`match_keywords`は、登録（`append_posted_items`）自体は妨げないが、
索引の構築（`build_posted_index`）時に無視され、一致判定に一切使われない
（安全側に倒す設計）。「型番など十分に一意な識別子なら1語でも可」という
例外は、プログラムで機械的に判定するのが難しい（型番かどうかを自動判定する
基準が無い）ため実装せず、常に2語以上を必須にしている。1語しかない固有の
商品名（例：「ぶんぶんチョッパー」）は、意味のある部分に分割して2語以上に
することで登録している（例：`["ぶんぶん", "チョッパー"]`）。

一般語（収納・掃除・キッチン・便利・ラック・ケース等）だけの組み合わせは、
プログラムでは判定できないため実行時のガードは設けていない。過去投稿を
登録する際に、ブランド名＋商品固有名詞を基本にすることで対応している
（下記「過去投稿の初期登録」参照）。

### 過去投稿の初期登録

`data/past_posted_items_seed.json`に、ブランド名＋商品固有名詞が明確に
確認できた22件を登録した（例：「マーナ シートケース」「tower
マグネットバスルームラック」「ウタマロクリーナー」等）。`item_code`・
商品URLが分からないため、いずれも`match_keywords`（該当する場合は
`product_name`も）で登録している。「tower マグネットバスルームラック」は
スクリーンショットで「ワイド」サイズと確認できたため、`match_keywords`に
`"ワイド"`を含めて「ラージ」等の別サイズと誤判定しないようにしている。

商品の種類・サイズ・個数が曖昧で、推測で登録すべきでないと判断したものは
`data/past_posted_items_unresolved.json`に候補として書き留める運用にした
（今回時点では該当する情報が無かったため空のまま）。本番の

```bash

```

`dedupe.append_posted_items`は、`item_code`・商品URL・商品名・
`match_keywords`のいずれか1つでもあれば登録を受け付ける（今回、
`match_keywords`だけのレコードも受け付けるように条件を追加した）。
